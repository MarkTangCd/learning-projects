真实执行与风控

Paper trading 撒了一个谎:"即时、全额、按我的价成交"。真实市场里,你只能发出订单——成不成、成多少、成在哪个价,由交易所说了算。

L8 你造的 tick 机器人里,买入就是一行算术:coin = cash / price。它假设你想要的价格必然、瞬间、全额兑现。真实执行把这三个假设全打碎:订单是异步的——你 SEND,然后必须READ BACK(回读)交易所返回的订单对象,再RECONCILE(对账)你以为的和实际发生的。

这一课的可见胜利 在 Binance 测试网(真订单、假钱)上走完一次订单生命周期:挂一张不会成交的限价单看它 open → 撤单看它 canceled;再打一张市价单看它真成交,然后对账出真实滑点与手续费。全程每张单都先过风控闸门 + 急停。

订单的生命周期

回测里"成交"是一个瞬间。真实订单是一个状态机,会走到下面某个终态——你的代码必须能处理每一条分支:

SENDcreate_order 发出,拿到 id
→
open挂在簿上,filled=0 或部分
→
closedfilled=amount 全成交
canceled你撤单 / 超时未成
rejected被拒:余额/精度/风控
partial只成一部分,剩下继续挂

ccxt 用一套统一订单结构把这些跨交易所抹平。下单后你要回读的关键字段:ccxt 订单结构

字段含义为什么 L8 看不到它
statusopen / closed / canceled回测没有"挂着"这个状态
filled / remaining已成 / 未成数量回测默认 filled=amount
average实际成交均价回测用你给的 price,不是市场吃到的价
fee真实手续费(maker/taker 不同)回测用一个固定费率近似

限价 vs 市价 —— 你在选"要价格"还是"要成交"

类型你得到什么你放弃什么角色
限价单 limit价格有保证(不超过你的价)成交没保证,可能一直挂着maker(挂单方,费率低)
市价单 market成交有保证(立即吃单)价格没保证,吃穿盘口=滑点taker(吃单方,费率高)

L8 的"即时必成交"其实偷偷用的是市价单的成交假设 + 限价单的价格假设——两头好处都要,现实里没有。

一张限价买单挂在市价下方 20%,刚发出后它的 status 最可能是?
对。买价远低于市场,没人愿意卖给你,单子就挂着(open, filled=0)。这正是回测里不存在、实盘里必须处理的状态。
不成交才对。你的买价比市场低 20%,没有卖方会以这个价成交,订单停在 open、filled=0,直到你撤单或市价跌下来。

SEND → READ BACK → RECONCILE

这是替换 L8"即时必成交"的新纪律。下单后永远不要相信 create_order 的即时返回就是最终结果——它可能还是 open。要 fetch_order 回读真相,再对账:

# SEND
o = ex.create_order(SYMBOL, "market", "buy", amount, None,
                    {"clientOrderId": cid})   # 幂等钥匙,呼应 L8
# READ BACK —— 别信下单回执,查订单簿里的真相
filled = ex.fetch_order(o["id"], SYMBOL)
# RECONCILE —— 我以为的 vs 实际发生的
slip_bps = (filled["average"] - assumed) / assumed * 1e4
print(filled["status"], filled["filled"], filled["average"], filled["fee"])
市价单成交后,给账户记账该用哪个价格?
对。average 是交易所吃单后实际给你的加权均价,和你下单前看到的 last 之间的差就是已实现滑点。用假设价记账 = 账户对不上。
用假设价会让账目失真。市价单吃穿盘口,真实成交价是回读到的 average;它减去下单前的 last 就是你这次付出的滑点成本。

风控闸门 + 急停(每张单的前置关卡)

执行深水区最贵的 bug 不是"少赚",是"下错单把账户打爆"。所以任何订单发出前都要过一道风控闸门,它有权拒绝:

  • 名义价值上限:amount × price ≤ MAX_NOTIONAL——挡住 fat-finger(多打一个零)。
  • 最小下单额:低于交易所 limits.cost.min 会被拒,提前挡下。
  • 急停 kill switch:一个开关(这里是一个 flag 文件),打开即秒拒一切新单——策略发疯、行情异常时你的红色大按钮。风控里最先、最便宜地检查。
测试网的真实坑(正是执行课该有的) Binance 现货测试网端点正在从 testnet.binance.vision 迁移到 demo-api.binance.com。ccxt 4.5.x 的 set_sandbox_mode(True) 仍指向前者——只要你的 key 也是在 testnet.binance.vision 上用 GitHub 登录生成的,两者匹配就能跑。若报 Invalid API-key,多半是 key 与端点不匹配:重新在同一站点生成 key,别混用主网 key。真实券商换端点/换鉴权是执行层的日常,你的第一个实盘 bug 大概率就长这样。

动手挑战:在测试网走完一次订单生命周期

你的第一张真订单(假钱) 脚本 practice/execution.py 已写好(测试网 + 代理 + 风控闸门 + 急停)。
① 拿密钥:去 testnet.binance.vision 用 GitHub 登录 → Generate HMAC Key → 两行 export:
export BINANCE_TESTNET_KEY="..." · export BINANCE_TESTNET_SECRET="..."
② 看余额:python execution.py balance(测试网自带一堆假 USDT/BTC)。
③ 挂单→撤单:python execution.py rest——看它 open(filled=0)再 canceled。
④ 真成交→对账:python execution.py fill——看 closed、真实 average、滑点 bps、手续费。
⑤ 试急停:python execution.py kill 再跑一次 fill——风控闸门应秒拒;unkill 解除。
