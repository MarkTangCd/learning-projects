幂等下单:断网重试为什么不能下重单

L9 你把订单发出去、回读、对账,一切在网络顺利时都对。但执行层最危险的一刻不是下单成功,而是下单成功了、可你不知道——响应在半路超时了。天真地重试,你就买了两次。

下单是一次异步写操作,跨一条不可靠的网络。create_order 的请求可能已经到达交易所并成交,但响应在返回你的路上超时。你的代码只看到一个 exception,它无法区分这两种情况:

  • A. 单没下成(请求没到)→ 你应该重试。
  • B. 单下成了,只是回执丢了(请求到了、响应丢了)→ 你绝不能重试。

问题是:从异常里你分不清 A 和 B。 而"重试一次网络写"正是账户被下双倍单的经典死法。

09:00:00.0 你 → 交易所 create_order(buy 0.01 BTC) 请求出发 09:00:00.3 交易所 ✔ 成交,BTC 已买入 09:00:30.0 交易所 → 你 ✗ 响应超时(网络抖动,回执丢了) 09:00:30.0 你的代码 except: → 天真重试 create_order(buy 0.01 BTC) 09:00:30.4 交易所 ✔ 又成交一次 —— 你现在持有 0.02 BTC ❌

解药:幂等钥匙(idempotency key)

让"重试"变安全的唯一办法:给每笔交易的意图配一把你自己生成的钥匙,随下单一起交给交易所。交易所承诺:同一把钥匙,最多只执行一次。 第二次带同样钥匙来,它拒绝(或原样返回第一张单),而不是新开一单。这把钥匙在 Binance / ccxt 里就是 clientOrderId。

你 L9 脚本里的"假幂等"(真 bug) L9 的 guarded_create 里那把钥匙是:
cid = f"l9-{int(time.time() * 1000)}"
它每次调用都用当前毫秒时间戳生成新值。重试时钟走了、cid 变了 → 交易所把它当全新一单 → 幂等形同虚设。幂等钥匙必须是"这笔交易是什么"的纯函数,绝不能含 time.time()。

正确的钥匙由意图决定——同一个意图,无论重试几次,钥匙都一样。呼应 L8:tick 循环里天然的意图 id 就是 (symbol, side, bar_ts)——"在这根 K 线上,买"这件事只该发生一次。

# 钥匙 = 意图的纯函数,重试时保持不变(不是墙上时钟!)
def intent_cid(side, price, tag="l9"):
    return f"{tag}-{side}-{str(price).replace('.', '_')}"
# L8 tick 循环里更自然:f"{symbol}-{side}-{bar_ts}"

o = ex.create_order(SYMBOL, "limit", "buy", amount, price,
                    {"clientOrderId": intent_cid("buy", price)})  # 同意图 -> 同钥匙
下面哪个 clientOrderId 能让断网重试安全?
对。幂等靠的是同意图→同钥匙。钥匙由 (symbol, side, bar_ts) 这类意图决定,重试多少次都是同一把,交易所据此去重。含时间戳的钥匙每次都变,等于没有幂等。
时间戳每次调用都变,重试时是一把新钥匙,交易所无从去重 → 照样下重单。幂等钥匙必须是交易意图的纯函数,不含 time.time()。

配套动作:超时后不要盲目重发

幂等钥匙让重发不会造成第二单,但更稳的做法是重发前先查真相。捕获超时后,别直接再 create_order——先用钥匙问交易所"这单到底下成没有":

try:
    o = ex.create_order(SYMBOL, "limit", "buy", amount, price,
                        {"clientOrderId": cid})
except ccxt.RequestTimeout:
    # 不知道 A(没下成)还是 B(下成了、回执丢了)。别猜,去查:
    existing = ex.fetch_order(cid, SYMBOL)   # 用 clientOrderId 回读
    if existing:                             # B:其实成了 -> 对账,别重发
        reconcile(existing)
    else:                                    # A:确实没下成 -> 用【同一把】cid 安全重发
        o = ex.create_order(SYMBOL, "limit", "buy", amount, price,
                            {"clientOrderId": cid})

两道保险叠在一起:先查把大多数情况解决;万一查询和重发之间又抖动,同一把幂等钥匙兜底,交易所不会给你开第二单。

create_order 抛了 RequestTimeout,最稳的下一步是?
对。超时无法区分"没下成"和"下成了但回执丢了"。先查(用 clientOrderId 回读),查到就对账、查不到才用同一把 cid 重发。这样任何一条路径都不会产生第二单。
新 cid + 盲目重发正是双倍单的做法:若原单其实已成交,你又下了一单。超时后要先查后发,且重发必须复用同一把幂等钥匙。

动手挑战:亲手撞一次幂等墙

看交易所把重复单挡下来 脚本已加好 dup 命令(用一张远低于市价、不会成交的限价单,同一个 clientOrderId 连发两次,安全):
① python execution.py dup —— 第一次创建成功;第二次带同一把 cid → 交易所拒绝重复(DuplicateOrderId)或原样返回同一张单;最后自动撤单。
② 想看"假幂等"如何翻车?把 intent_cid 临时改成 f"l9-{int(time.time()*1000)}",再跑一次 dup —— 两次会拿到两个不同 id(下了重单)。看完改回去。
把两次的输出贴给我,我们对一下:交易所到底是拒绝了重复,还是原样返回了第一张单?(两种都算幂等成立,但账要不同地对。)
